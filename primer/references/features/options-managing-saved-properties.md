###  Options: Managing Saved Properties

Hovering the cursor over the Save P (or SP i/j ) button maps the Save Props popup in which you can select Options to control saved properties.
 
The Saved properties panel may also be invoked directly from the [Display] popup, or by keyboard short-cut key "~" (Tilde).

| The effect on a saved property of changing model contents <br>In order to be economical of memory the model-dependent data in a saved property is stored in "runlength encoded" form. This utilises the fact that in most models a sequence of items will all have the same visual attributes, for example all elements in a part will tend to have the same colour, transparency, etc. Therefore for a given item the property data each row is saved (qualitatively) as:<br> <br><br>| Label A | Label B | Property information |<br>| --- | --- | --- |<br><br> <br>All items lying in the label range A to B implicitly have the same Blanking, Colour, Transparency and Display mode.<br> <br>Therefore when the model is changed the following happens:<br> <br><br>| **Change made to model** | **Consequence when a saved property is restored** |<br>| --- | --- |<br>| Items in the range A to B are deleted | If the deleted items lie within this range, but do not include either A or B themselves, then there is no effect. <br> <br>If either item A or B are deleted then the whole of this "row" of properties is lost, and on a subsequent restore items within this range will not be updated. |<br>| New items are added | Items added within an existing label range A to B will automatically be included within that range, and their properties will be updated on a restore. <br> <br>Items outside any saved range will not be updated since they were not known about when the property was saved. <br> <br>Where new items overlap an existing A .. B range then only the subset lying within that range will be updated. |<br>| Existing items are renumbered | Internally PRIMER stores the item "object" rather than just its label, so renumbering objects automatically updates their label ranges in saved property rows of data. <br> <br>Therefore if existing label range A .. B is modified to A' .. B' all items within that new range will be updated as before, but this might or might not include the same range of items. <br> <br>If the new range is invalid, for example B' is now less than A', then no update will take place. |<br><br> <br>It will be clear that the logic above is not perfect, and that changing a model may well invalidate some or all saved properties. This is an inevitable consequence of the compact storage method used, and is considered to be a reasonable compromise. Storing data in a "change resistant" form would require many orders of magnitude more memory, and this could have unacceptable side-effects on the performance of the code. |
